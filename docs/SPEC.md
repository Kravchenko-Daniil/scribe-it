# scribe-it — спецификация продукта

> Что строим. Как и в каком порядке мигрировать — `docs/PLAN.md`.

## Суть
Сервис превращает медиа в текст. На входе — источник (файл или ссылка), на выходе — транскрипт каждого видео/аудио, что в источнике есть. Одна задача, одно место, где она выполняется.

## Архитектура
**Центр продукта — API.** Бот и сайт — тонкие клиенты, своей логики не имеют, только зовут API.

```
Telegram-бот ┐
             ├─HTTP→  API  ─→  ядро: источник → скачать → ffmpeg→opus → Scribe → текст
Сайт (позже) ┘                 кеш
```

- **API** — единственное место, где идёт работа.
- **Бот** — HTTP-клиент API. Принял файл/ссылку → отдал API → вернул юзеру `.txt`.
- **Сайт** — второй клиент, делает то же самое. Реализуется отдельным заходом позже.

## Вход
Любой источник сводится к списку медиа-элементов. Поддерживаем:

| Источник | Одиночный | Множественный |
|---|---|---|
| Файл в Telegram | да | — |
| YouTube | видео | плейлист → все ролики |
| Яндекс.Диск | файл | папка → все файлы |
| Google Drive / прямой http | файл | — |

Папку и плейлист сервис перебирает сам. Снаружи никаких циклов.

## Пайплайн (ядро)
`источник → resolve в список элементов → на каждый: скачать (yt-dlp) → извлечь аудио (ffmpeg → opus 32k mono) → ElevenLabs Scribe → рендер текста`

Scribe-параметры: `model_id=scribe_v1`, `diarize=true`, `timestamps_granularity=word`. Язык определяется автоматически; подсказки (язык, число спикеров, имена) опциональны и передаются в запросе.

## Выход
- **Пользователю** (бот, сайт) — только `.txt`: чистый текст, разбитый на абзацы и по спикерам. Один `.txt` на каждый элемент источника.
- **API наружу** — JSON: `{ "status": "queued|running|done|error", "items": [ { "index": 0, "name": "1.mp4", "stem": "1", "text": "...", "status": "done|error", "stage": null, "error": null }, ... ], "error": null }`. Элемент папки/плейлиста может упасть индивидуально (`status="error"`), при этом джоба остаётся `done`, если успешен хоть один. Поле `stage` (`null|download|audio|scribe`) — прогресс одиночного элемента для клиента. Поле `stem` — slugified-имя без медиа-расширения; клиент именует выдаваемый файл `<stem>.txt` (`name` может нести `.mp4` — только для отображения). `opus_hash` — внутренний provenance, в наружную форму НЕ входит.

## Кеш
Транскрипция — единственное, что стоит денег. Кешируем результат, чтобы не платить дважды и иметь возможность вернуться к материалу.

- Храним **только сырой ответ Scribe** (`.json`) как единственный первоисточник; `.txt`/`.srt` пересобираются на чтении через `to_paragraphs`/`to_srt`.
- **Ключ** — `sha256(opus)` (выход ffmpeg, не источник) + параметры запроса к Scribe: язык, число спикеров, `biased_keywords` (= отсортированные имена спикеров). Display-имена спикеров применяются на рендере и в ключ НЕ входят. Разные параметры = разные записи.
- **TTL 30 дней**, фоновая очистка просроченного.
- Дедуп по ключу заменяет старую логику `skip`/`checkpoint` — повтор того же аудио пропускает оплачиваемый шаг Scribe (без оплаты). Скачивание и ffmpeg→opus всё равно выполняются (URL не кешируется), так что «мгновенно» относится только к шагу Scribe.

## API (контракт)
- `POST /jobs` ← один из `{ "url" | "local_path" | multipart-файл }` (ровно один источник, иначе 400). Опционально `language`, `num_speakers`, `speaker_names`. → `{ "job_id": "..." }`. `local_path` — основной путь бота (один хост, без перезаливки); валидируется как путь под staging-каталогом. `num_speakers` — часть ключа кеша.
- `GET /jobs/{id}` → `{ "status": "queued|running|done|error", "items": [ { "index", "name", "stem", "text", "status", "stage", "error" } ], "error": null }`. `text` — готовый транскрипт для `done`-элемента (пустой для `error`); `stem` — имя выдаваемого `<stem>.txt`.
- Асинхронно (job-режим): часовое видео обрабатывается минуты, держать запрос открытым нельзя.
- Загруженные файлы передаются между ботом и API по локальному пути (`local_path`) — общий staging-каталог на одной ФС с download-каталогом локального Bot-API, без повторной перезаливки. Это согласованная точка handoff: любой будущий клиент на том же хосте (сайт) держит тот же инвариант; путь должен лежать под staging-каталогом (иначе API отклоняет с 400).

## Структура репозитория
- `bot.py` — усохает до HTTP-клиента API.
- `api.py` — HTTP-сервис с job-моделью.
- `core/` — единственное место логики (бывшие `downloader.py`, `scribe.py`, `storage.py`): resolve источника, скачивание, аудио, Scribe, рендер форматов, кеш.
- **Удалить:** `yadisk_batch.py` (его смысл — папка с Диска — теперь штатный вход).
- **Вынести из репо в `D:\lab\content`:** `arsen_batch.py`, `arsen_state/`, `arsen_user.session` — это личная разовая задача (выкачка Telegram-канала через user-сессию), не часть продукта.

## Порядок сборки
1. Ядро (`core/`): resolve-источника, пайплайн, рендер форматов, кеш.
2. API: job-модель, эндпоинты, кеш.
3. Перевод бота в HTTP-клиента API.
4. Чистка: удалить `yadisk_batch.py`, вынести arsen в `D:\lab\content`.
5. Сайт — отдельным заходом позже.
